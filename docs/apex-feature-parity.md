# Oracle APEX feature parity

This page compares pgkiln with **Oracle APEX 26.2**, area by area (rows marked 26.1 or 26.2 name the release that brought the feature). It's meant to be
honest: it shows what a team moving from APEX can use today and what is still missing. Pick an
open item and open an issue or pull request; see [CONTRIBUTING.md](../CONTRIBUTING.md).

Legend: ✅ available · 🟡 partial (see notes) · ❌ not yet · ➖ not planned (a deliberate choice,
or better served by the PostgreSQL ecosystem; see the notes and [extensions](guide/15-extensions.md))

## Different on purpose

- **Mail services instead of the instance's SMTP server.** APEX sends mail through `UTL_SMTP` with
  a user name and password only (no OAuth2), so Microsoft 365 after the end of basic authentication
  needs a relay, and providers such as Amazon SES or Resend only work through their SMTP gateways.
  pgkiln sends through SMTP with a password or OAuth2, Microsoft Graph, Amazon SES or a provider's
  HTTP API, chosen per application (sprint 50; the earlier "no e-mail" decision was reversed). With a
  mail service, applications can offer a built-in *Forgot password?* (sprint 55), which APEX apps
  don't have out of the box.
- **PostgREST instead of ORDS**, and no web listener at all: the pgkiln server talks to
  PostgreSQL directly.
- **Row level security instead of VPD**, and one set of policies for the UI and the API.
- **JSON or YAML export instead of SQL or APEXlang** files.
- **Server-rendered HTML** with progressive enhancement: pages work without JavaScript, and no
  inline scripts are needed.

## Where pgkiln goes further

Small but real differences, for teams comparing the two:

- Open source (Apache-2.0), on any PostgreSQL 15+, including every managed service.
- A strict CSP by default (no inline scripts or styles), and a security regression suite that runs in CI.
- Responsive layouts verified automatically at four screen sizes.
- The theme follows the device's light/dark setting automatically, and the choice is saved per user.
- A built-in *My account* page (own password, theme, language).
- (sprints 126–128) **Two-factor sign-in for the builder** without an identity provider: passkeys (WebAuthn; sign-in with a
  passkey alone), authenticator apps (TOTP), recovery codes, a policy for administrators, all developers or a
  workspace's developers with a grace period, and lockout recovery on the
  command line ([chapter 3](guide/03-builder.md#two-factor-sign-in)). APEX relies on the identity provider.
- (sprints 130–131) **Two-factor sign-in for application users**: per application and per role, with authenticator
  apps, passkeys and recovery codes, added while signing in when required, a code by e-mail as a fallback, step-up
  before sensitive pages (an authorization scheme's *Second step within*) and REST API tokens only after a second step
  ([chapter 8](guide/08-security.md#two-factor-sign-in)).
  APEX's application authentication schemes have no second factor.
- (sprint 132) **Proof that the identity provider did multi-factor sign-in**: a provider can be required to say so in
  the ID token's `amr` / `acr` or the SAML `AuthnContextClassRef`, step-up goes back to it for a fresh multi-factor
  sign-in, and pgkiln's own second step can follow a provider that cannot enforce MFA
  ([chapter 8](guide/08-security.md#multi-factor-sign-in-at-the-identity-provider)). APEX trusts the provider's policy.
- (sprint 133) **Lockout checks**: Instance settings and `pgkiln admin check` warn before anyone is locked out: secrets
  the instance key can't decrypt, a key without a confirmed backup, clock drift that breaks authenticator codes,
  passkeys of another domain (also before a move, with `--url`) and single sign-on without a break-glass
  administrator; `pgkiln admin rotate-key` changes the instance key in one transaction
  ([chapter 3](guide/03-builder.md#lockout-checks)).
- One RLS policy set protects both the web UI and the REST API.
- An import can be checked before it commits (`pgkiln import --check`): SQL that names a missing
  table or column refuses the deployment instead of failing at run time.
- E-mail through SMTP with OAuth2, Microsoft Graph, Amazon SES and HTTP APIs, not only SMTP with a password.
- (sprint 85) A **Form Designer** region ([chapter 4](guide/04-pages-and-regions.md#form_designer-form-designer)): the
  application's administrators build and publish data entry forms in the running application, on the tables and
  columns the developer offers, with grants, row level security and lost update detection applying.
